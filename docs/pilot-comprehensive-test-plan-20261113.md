## 6. 本轮重点专项

### 6.1 防复发专项（每条必须有负控制测试）

| ID | 场景 | 通过标准 | 负控制 |
| --- | --- | --- | --- |
| R-01 | `energy/tasks` 无 ALS 上下文 | 真实账号 200，返回 items | 单测里去掉 `{system:true}` 必须红 |
| R-02 | 改派/抢单/部门变更通知 | 通知记录 `delivered=true` 或明确 43101，不得 STUB | 省略 `recipientKind` 仍按 worker 解析 |
| R-03 | 订阅模板 ID | `app.js` 与后端 `.env` 完全一致 | 人为改错一位，门禁脚本必须失败 |
| R-04 | 一次性订阅额度 | 授权后不自发测试消息；真实派单 `errcode=0` | 连续发两条第二条必须 43101 |
| R-05 | pilot 隐藏路由 | `/monitor`、`/transport` 重定向 `/dashboard` | 直接输入 URL 也不可进入 |
| R-06 | AI embedding 隔离 | 关闭时核心流程达标；开启时不得拖垮建单 | 开启后复现连接池超时必须被记录为缺陷 |

### 6.2 权限与租户隔离

- 角色 × 动作矩阵：admin / operator / worker / 自定义角色 × 各模块读/写/删/确认/导出；
- 每个受限动作至少 1 条 403/401 负向；
- 跨租户 IDOR：用 UAT-A token 读/改 UAT-B 的资源，必须 404/403；
- RLS 验证：直连数据库以 `youfu_app` + 错误 `app.tenant_id` 查询必须 0 行；
- 权限变更后立即生效，旧 token 不保留旧权限。

### 6.3 并发与幂等

| ID | 场景 | 目标 |
| --- | --- | --- |
| C-01 | 10 并发建单 | p95 < 3s，0 个 500 |
| C-02 | 50 并发建单 | 0 个 500，无连接池超时 |
| C-03 | 20 人同时抢 1 单 | 只有 1 人成功，其余 409 |
| C-04 | 并发领用同一耗材 | 库存不为负，总量守恒 |
| C-05 | 重复提交同一结算单 | 唯一约束生效，不重复计费 |
| C-06 | 同一工单并发流转 | 只有合法状态迁移成功，无覆盖写 |
| C-07 | 重复 webhook / 重复回调 | task_ref 幂等，不重复建单 |

### 6.4 通知与微信

- 模板 ID 一致性门禁（构建/部署前脚本）；
- `insertNotification` 全部调用点检查 `recipientKind`；
- 真实微信：授权→真实派单→`delivered=true`→用户微信确认；
- 失败码覆盖：43101 / 47003 / 40003 / 40014 的日志与提示；
- 通知点击跳转、未读计数、全部已读；
- 重启丢失风险：进程重启时内存中的 `wechatPendingQueue` 是否丢消息（记录为可靠性缺陷并评估）；
- 通知与工单/巡检/运送/志愿者的事件一致性。

### 6.5 性能

| ID | 场景 | 目标 |
| --- | --- | --- |
| P-01 | 10 并发建单 × 20 单 | p95 < 3s，成功率 100% |
| P-02 | 1000 条工单列表首页 | p95 < 1.5s |
| P-03 | 1000 条深分页 offset=900 | p95 < 1.5s |
| P-04 | 50 并发建单 | 0 个 500，p95 记录基线 |
| P-05 | 1 小时持续混合流量 | error_rate 0，内存无持续上涨 |
| P-06 | 5MB 上传 / 5MB+1 | 前者成功，后者 413 |
| P-07 | 工作台聚合四源 | p95 < 500ms，单源失败不拖垮整体 |
| P-08 | AI embedding 开/关对比 | 开启不得导致建单 500；否则列 P1 |

### 6.6 安全

- 未登录访问全部受保护 API：401；
- JWT 过期/伪造/换租户：401/403；
- 水平越权：worker 读他人任务、通知、结算；
- 垂直越权：worker 调 admin/operator 接口；
- XSS：工单标题/描述/反馈/公开报修；
- SQL 注入：筛选参数、排序、导出；
- 上传：类型伪装、路径穿越、超大文件、双扩展名；
- Webhook：HMAC 错误/过期/重放；
- 限流：登录、公开报修、上传、自检；
- 敏感信息：日志/响应/导出中的手机号、openid、token；
- CORS/安全响应头/错误堆栈泄露。

### 6.7 可靠性与恢复

| ID | 场景 | 通过标准 |
| --- | --- | --- |
| REL-01 | 负载中重启后端 | 重启后健康，无脏数据，任务可继续 |
| REL-02 | 备份→临时库恢复 | 行数、RLS、抽查数据一致 |
| REL-03 | 巡检计划调度补跑 | 停机期间到期计划重启后生成 |
| REL-04 | SLA 扫描/升级 | 到期任务生成预警，重复扫描不重复通知 |
| REL-05 | 数据库连接池打满 | 请求快速失败/降级，不雪崩 |
| REL-06 | 微信接口超时 | 不阻塞主流程，记录失败，可重试 |
| REL-07 | 前端发布回滚 | 旧版本可回退，静态资源不 404 |

### 6.8 真机与兼容性

- iPad（iPadOS 微信）与 HarmonyOS（微信）各走查：
  - 登录 → 工作台 → 通知 → 开启通知 → 任务详情 → 抢单 → 巡检/巡更 → 陪检 → 运送 → 志愿者 → 资产扫码 → 我的；
- 检查：安全区、横竖屏、字体、按钮可点区域、图片/语音上传、扫码、下拉刷新、弱网重试；
- 真机授权后真实派单微信到达；
- PC 浏览器：Chrome/Edge 最新版，1366×768 与 1920×1080；
- 小程序基础库最低版本与 `requestSubscribeMessage` 可用性。

### 6.9 可观测性与发布门禁

- `/health` 与 `/health/ready` 均 200；DB 断开时 `/health/ready` 503；
- 每个响应有 `X-Request-Id`，错误日志可按 request id 追踪；
- 关键错误（500、通知失败、webhook 验签失败）有日志与告警；
- 部署后冒烟：登录、建单、列表、通知、隐藏路由；
- 回滚脚本与备份可用。

## 8. 缺陷处理规则（按全局铁律）

发现缺陷后必须先回答四问，答不清不改代码：

1. 属于哪一层：数据 / 契约 / 共享逻辑 / 调用方 / 流程门禁？
2. 为什么现有测试/门禁没拦住？
3. 修的是根因层还是表象？
4. 删掉修复后，哪条测试必须变红？

修复要求：

- 根因修复，不打补丁、不加临时特判、不双轨；
- 必须带负控制测试（happy path 不算）；
- 共享口径改共享层；
- 全量测试 0 fail；
- 需要部署的给出线上证据；
- 无法根治时明确标注，不冒充完成。

缺陷分级：

```text
P0 数据丢失/越权/核心流程不可用 → 立即停测修复
P1 核心模块阻塞且无绕过 → 当日修复
P2 局部功能异常有绕过 → 本轮修复或书面豁免
P3 文案/样式 → 记录，可下轮
```

## 13. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 真实微信一次性授权被误消耗 | 真实到达验证失败 | 授权后不自发测试消息；先授权再派单 |

| soak/长稳压测影响 pilot | 用户可感知变慢 | 限流、避开使用高峰、可随时中止 |
