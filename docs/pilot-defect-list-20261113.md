# Pilot 新一轮缺陷清单（2026-11-13）

> 规则：每条必须写清层级、为什么测试没拦住、修的是不是根因、删除修复后哪条测试必须红。

## D-01 抢单并发失败者返回 404，客户端无法识别“手慢了”

- 级别：P2（体验/契约）
- 状态：已修复
- 层级：调用方 + RLS 可见性 + API 契约
- 现象：3 人同时抢 1 单，赢家 200，另外两人 404 `work order not found`。
- 根因：抢单端点使用抢单大厅 RLS（`app_claim_hall=1` 仅见未指派行）。
  赢家提交后，后到请求看不到该行，`findOneForUpdate` 返回 null，
  `claimWorkOrder` 抛 NOT_FOUND。小程序只把 409 翻译为“手慢了”，404 会显示英文
  `work order not found`。
- 为什么之前没拦住：单测/HTTP 测试只覆盖单请求成功路径，没有并发抢单的失败者断言；
  E2E 也没有真正的多 token 并发。
- 修复：`claimWorkOrder` 在抢单作用域内看不到行时返回 `409 CONFLICT`
  （动作语义：已离开抢单池），不再 404；工人不存在仍保持 404。
- 负控制：
  - `src/test/claimThroughGates.test.ts` ⑨：不可见单必须 409；
  - 深度 E2E：3 人并发抢单必须 1×200 + 2×409。
- 删除修复后变红的测试：`claimThroughGates.test.ts` ⑨ + `pilot-round2-deep-e2e.mjs` 抢单并发用例。

## D-02 改派/抢单/部门变更通知漏传 recipientKind，微信永远 STUB

- 级别：P1（真实通知不可达）
- 状态：已修复
- 层级：调用方（insertNotification 入参）
- 根因：三处调用未传 `recipientKind: 'worker'`，`resolveOpenid` 走进账号分支，
  `HQ016` 不是 UUID → openid=null → 诚实 STUB。
- 为什么之前没拦住：单测的 `baseInput` 总是带 `recipientKind`；真实 E2E 只断言
  `delivered=false`，没有断言“不得为 STUB”。
- 修复：
  - 三处调用补 `recipientKind: 'worker'`；
  - `resolveOpenid` / 手机号解析默认按 worker 处理；
  - 新增回归用例：省略 `recipientKind` 仍按 worker 解析。
- 负控制：`notify.test.ts` 新增“省略 recipientKind 仍解析 openid”用例。
- 删除修复后变红的测试：该新增用例 + 真实派单 E2E。

## D-03 energy/tasks 缺少 system 作用域，工作台第四源 500

- 级别：P1（工作台告警/功能缺失）
- 状态：已修复
- 层级：共享数据访问层（withTenantClient 调用参数）
- 根因：energy 路由挂在 authMiddleware 之前，没有 ALS 上下文，但多个
  `withTenantClient` 未传 `{ system: true }` → `MISSING_AUTH_CONTEXT` 500。
- 为什么之前没拦住：测试 mock 了 withTenantClient，不校验 opts；E2E 没覆盖
  “无 ALS 上下文的路由”。
- 修复：energy 路由统一 `withEnergyTenant()`，显式 system；新增 E07b 断言所有 DB
  访问必须 system。
- 负控制：`energyCollection.http.test.ts` E07b。
- 删除修复后变红的测试：E07b。

## D-04 订阅模板 ID 双源漂移，微信不弹授权框

- 级别：P1（真实微信不可用）
- 状态：已修复
- 层级：配置契约（小程序 ↔ 后端）
- 根因：小程序 `app.js` 仍是旧模板 `XKVK...`，后端 `.env` 是 `jfu0s...`；
  微信对旧模板直接拒绝，后端发送新模板又未授权 → 43101。
- 为什么之前没拦住：模板 ID 存在两个配置源，没有一致性门禁；授权测试只看后端。
- 修复：小程序模板 ID 与后端对齐；授权失败显示真实状态。
- 待补：部署门禁脚本自动比对两处模板 ID（当前人工核对一致）。
- 删除修复后变红的测试：真机授权弹窗 + 真实送达。

## D-05 授权后自动发自检，消耗唯一一次订阅额度

- 级别：P2（真实派单通知失败）
- 状态：已修复
- 层级：调用方流程（小程序授权后动作）
- 根因：一次性订阅每次只能发 1 条，授权后立即自检会把额度用掉，
  真实派单时又变 43101。
- 修复：授权成功不再自动自检，额度留给真实派单。
- 负控制：真机授权 → 真实派单 → `errcode=0`。

## D-06 微信 pending 队列在内存，重启/崩溃会丢待补投递通知

- 级别：P2（可靠性）
- 状态：未修复（本轮记录，需书面豁免或后续排期）
- 层级：数据/基础设施（delivery outbox）
- 根因：`wechatPendingQueue` 是进程内数组，响应 finish 后异步补投递；
  进程崩溃或重启会丢失尚未发送的条目，且没有持久化凭证。
- 为什么之前没拦住：soak 只测稳定运行，没有“提交后立即杀进程”的测试。
- 建议根因修复：落 `notification_outbox` 表，投递状态机 + 重试 + 死信；
  不要在请求内直接发外部 HTTP。
- 本轮处理：记录风险；pilot 低并发下窗口极小，但需书面接受。

## D-10 AI embedding 与建单共用资源，开启后 p95 8s

- 级别：P2（性能/稳定性）
- 状态：已知，主流程配置为关闭
- 层级：服务资源隔离
- 证据：
  - 关闭：20 单 / 10 并发，p95 278ms，0 错误；
  - 开启：同场景 p95 8011ms，p99 8085.7ms，上一轮还出现连接池超时 500。
- 根因：embedding 外部调用与建单请求共用连接池/进程资源，外部延迟直接放大建单尾延迟。
- 建议根因修复：embedding 独立队列 + 独立并发/连接池 + 超时熔断，建单只入队不等待。
- 本轮处理：默认关闭；生产若开启必须先做资源隔离。
