# 第三轮全模块集成测试方案（2026-11-13）

## 0. 目标

对 pilot 做一轮**以“跨模块业务闭环 + 全功能点 + 故障注入”为核心**的全面测试，而不是把上一轮的模块用例再跑一遍。

三个必须回答的问题：

1. 每个模块自身的业务流程是否完整闭环？
2. 模块之间的业务逻辑是否真的流转正常（不是各测各的）？
3. 小程序所有页面/功能是否正常，真机上是否可用？

本轮还要主动找新问题；如果确实没有新的 P0/P1/P2，必须用覆盖率和证据说明“为什么可以判定没有”，而不是只写“全部通过”。

---

## 3. 测试模型

```text
C：跨模块业务链（16 条）
F：功能点清单（PC 页面/按钮/表单 + 小程序页面/动作 + API）
X：故障注入（15 类）
I：数据不变量（10 条）
N：非功能抽检（性能/安全/可靠性）
```

### 3.1 跨模块业务链（C1–C16）

每条链必须从“用户动作”开始，到“业务结果 + 数据落库 + 通知/统计”结束，并对中间每个状态断言。

| ID | 业务链 | 关键断言 |
| --- | --- | --- |
| C1 | 公开报修 → 自动派单 → 师傅接单 → 到场/处理 → 领料 → 复核 → 完成 → 结算确认 → 评价 | 工单状态链完整；库存扣减；结算金额=明细合计；评价回写；通知落库 |
| C2 | 巡检异常 → 生成预警 → 转工单 → 派单 → 处理 → 复核 → 结算 | 巡检单 exception；工单 source 关联；预警可追踪；结算可入账 |
| C3 | 资产故障 → 工单 → 维修 → 维保记录 → 结算 | 资产状态变化；工单关联资产；维保记录归属正确 |
| C4 | 设备档案 → 维保计划 → 到期/执行 → 维保记录 → 统计 | 计划日期、执行人、费用正确；列表/统计一致 |
| C5 | 巡更任务 → 漏检 → 预警/异常 → 处理 | 漏检状态；是否生成预警按实际契约断言；任务不可再签到 |
| C6 | 应急预案 → 关联资产/场景 → 触发/演练记录 → 查询 | 预案字段完整；关联资产有效；删除被引用预案的行为符合契约 |
| C7 | 志愿者活动 → 报名 → 签到 → 签退 → 核销 → 统计/时长 | 名额递减；重复报名拒绝；截止后拒绝；时长计算正确 |
| C8 | 运送单 → 抢单 → 接单 → 运输轨迹 → 送达凭证 → 完成 | 承运人唯一；轨迹有序；凭证落库；状态不可回退 |
| C9 | 陪检登记 → 工单 → 派单 → 完成 → 通知 | escort 工单类型；派单规则命中；通知可达 |
| C10 | 工作流版本变更 → 在途单锁旧版 → 新单新版 → 非法定义拒绝 | 在途单按旧版流转；新单按新版；非法状态图 422 |
| C11 | 派单规则变更 → 新单路由变化 → 术语变更 → PC/小程序文案变化 | 规则优先级生效；术语即时生效；旧单不重派 |
| C12 | 权限/角色变更 → 菜单/API 立即生效 → 旧 token 不保留旧权限 | 403 立即生效；权限回收后不可绕过 |
| C13 | 账号停用/删除 → 登录失败 → 名下任务处理 | token 失效；任务可转派；历史归属可追溯 |
| C14 | 结算确认 → 工单/库存锁定 → 作废 → 解锁 | 确认后不可改；作废后按契约解锁；金额快照不丢 |
| C15 | 通知中心 → 微信订阅 → 站内/微信一致性 → 已读/未读 | 授权一次只发一条；43101 可解释；未读数准确 |
| C16 | 反馈/评价 → 统计/过程挖掘 → 导出 | 统计口径一致；导出内容与列表一致；无 PII 泄露 |

### 3.2 功能点清单（F）

先自动生成清单，再逐项执行并打勾：

- **PC**：每个菜单页的页面加载、查询、筛选、分页、表单校验、提交、编辑、删除、导出/导入、空态、错误态、按钮权限；
- **小程序**：39 个页面的进入、返回、下拉刷新、主按钮、表单、上传、扫码、定位、通知；
- **API**：`src/routes/*.ts` 全量路由盘点，每个写接口至少 1 条成功 + 1 条未授权/越权 + 1 条非法参数；
- **配置类**：派单规则、术语、系统配置、角色权限、流程版本的增删改查与生效范围。

覆盖率目标：

```text
PC 功能点执行率 ≥ 95%，核心路径 100%
小程序 pilot 可达页面 100%，页面动作 ≥ 90%
API 写接口负向覆盖 100%
```

### 3.3 故障注入（X1–X15）

| ID | 注入 | 期望 |
| --- | --- | --- |
| X1 | 同一表单连续双击/重复提交 | 只产生 1 条业务数据或幂等返回 |
| X2 | 两个账号同时编辑同一记录 | 一方成功，另一方冲突提示，不静默覆盖 |
| X3 | 使用过期/伪造 token | 401，不泄露数据 |
| X4 | 流程中途回收权限 | 下一步立即 403 |
| X5 | 删除被草稿引用的主数据 | 明确 4xx，不产生脏数据 |
| X6 | 在途单遇到流程版本变更 | 按旧版走；新单按新版 |
| X7 | 派单规则中途变更 | 只影响新单，不重派在途单 |
| X8 | 微信接口返回 43101/47003/超时 | 主流程不阻塞，记录可追踪 |
| X9 | 上传超大/伪装类型/路径穿越 | 拒绝，文件不落盘 |
| X10 | 数据库唯一约束冲突 | 明确 409，不 500 |
| X11 | 分页边界 0/1/最后页/超界 | 不报错，不重复/漏数据 |
| X12 | 超长文本/emoji/HTML/JS | 正常保存或明确限制；XSS 不执行 |
| X13 | 断网/弱网/切网 | 有加载态/重试，不重复提交 |
| X14 | 小程序切后台再回来 | 状态不丢，不重复刷新/提交 |
| X15 | 服务重启/外部依赖超时 | 可恢复，不雪崩 |

### 3.4 数据不变量（I1–I10）

每条业务链结束后统一校验：

```text
I1 库存：期初 + 入库 - 出库 - 领用 + 退库 = 当前库存
I2 结算：sum(明细金额) = 表头 total；item_count 一致
I3 工单状态与最新 ticket_event 一致；时间戳顺序合法
I4 一次业务事件只产生一条对应 in_app 通知；微信仅在实际尝试时落凭证
I5 domain_event / notification 无孤儿
I6 跨租户查询零泄漏
I7 worker.load 与在途指派数量一致（按现有口径）
I8 上传文件 URL 可访问且租户归属正确
I9 审计字段（created_by/updated_by/时间）完整
I10 工单/巡检/运送的 def_version 与创建时版本一致
```

### 3.5 非功能抽检（N）

- 10 并发建单 p95 < 3s；
- 1000 条列表 p95 < 1.5s；
- 安全回归：越权、IDOR、XSS、上传、Webhook；
- 负载中重启；
- 备份恢复（如本轮有 schema/部署变更）。

## 8. 缺陷处理规则

沿用全局铁律：

1. 先定位层级：数据 / 契约 / 共享逻辑 / 调用方 / 流程门禁；
2. 回答“为什么现有测试没拦住”；
3. 修根因，不打补丁、不双轨；
4. 必须带负控制测试；
5. 全量测试 0 fail；
6. 需要部署的给线上证据；
7. 无法根治的明确标注，不冒充完成。

缺陷分级：

```text
P0 数据丢失/越权/核心流程不可用 → 停测修复
P1 核心模块阻塞无绕过 → 当日修复
P2 局部异常有绕过 → 本轮修复或书面豁免
P3 文案/样式 → 记录
```

## 10. “没有新问题”时的总结标准

如果本轮没有发现新的 P0/P1/P2，最终报告必须包含：

1. 实际执行的业务链数量 / 通过率；
2. PC 功能点执行率、未执行项及原因；
3. 小程序页面/动作覆盖率；
4. API 写接口负向覆盖数；
5. I1–I10 校验结果；
6. 全量测试、构建、类型检查结果；
7. 真机与真实微信证据；
8. 残余风险（P2 豁免、环境限制、未覆盖场景）；
9. 明确结论：“未发现新的 P0/P1/P2，置信度来自以上覆盖，而不是‘跑了一遍没报错’”。

## 11. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 业务链之间数据互相污染 | 每条链独立租户/独立前缀，链结束清理 |
| 真实微信授权被消耗 | 授权后不自发测试消息，先授权再派单 |
| 设备临时不可用 | 15:00 固定窗口，准备第二台设备 |
| 配置变更影响其他链 | 只在独立 UAT 租户改流程/规则/权限 |
| 故障注入导致服务不稳 | 限流、可中止、测试前备份 |
| 时间不足 | P0 链优先，P2 功能点可下轮 |
